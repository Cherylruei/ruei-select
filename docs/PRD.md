## 一、產品概述

### 1.1 產品定位

芮選系統是一個以 LINE 生態系為核心的代購賣場管理平台，幫助代購賣家從手動管理 LINE 群組訂單，升級為系統化的商品管理、訂單追蹤、配貨出貨流程，並內建 AI 文案優化與匯率換算功能。

### 1.2 核心價值主張

> 讓代購賣家把時間花在選品和顧客關係上，而不是手動整理訂單和撰寫文案。

### 1.3 競品分析

| 功能 | 樂樂系統 | 芮選系統 |
|------|----------|----------|
| 賣場管理 | ✅ | ✅ |
| 商品上架 | ✅ | ✅ |
| 訂單管理 | ✅ | ✅ |
| LINE 整合 | 部分 | ✅ 深度整合 |
| AI 文案優化 | ❌ | ✅ |
| 匯率自動換算 | ❌ | ✅ |
| 數據分析 | 基礎 | ✅ 行為分析 |

## 二、目標用戶

### Persona A：台灣本地代購賣家（主要）

- **背景：** 在台灣經營代購，商品來源為日本 / 英國 / 台灣大批發賣家
- **現狀：** 未購買任何代購管理系統，全程透過 LINE 群組和私訊手動操作
- **規模：** 固定顧客約 20 人，月訂單約 50 筆
- **痛點：**
  - 容易漏單，無法系統化追蹤每筆訂單狀態
  - 配貨判斷費時，需自行記憶哪個客人的哪件商品到貨
  - 商品文案需手動從廠商群組複製再改寫
  - 偶爾有外幣商品需手動換算成本
- **目標：** 降低手動作業量、減少漏單、提升顧客體驗

### Persona B：海外代購賣家（次要）

- **背景：** 旅居海外（如日本），代購當地商品回台灣
- **現狀：** 曾使用樂樂等付費系統，但功能有缺口
- **痛點：**
  - 日幣商品常態需要換算台幣成本
  - 現有系統缺乏 AI 文案功能
- **目標：** 匯率自動換算 + AI 文案，減少重複性作業

**共同結論：** 兩種賣家核心需求一致，匯率換算內嵌於商品上架流程，不需要分開設計。

## 三、系統架構

### 3.1 三層介面

```
商家後台  /admin/*
  商家登入後使用
  管理商品（依廠商分類）、訂單、顧客審核、配貨、出貨、數據分析

顧客前台  /store/{slug}/*
  顧客登入後使用
  瀏覽商品（依商品類型分類）、下單、查詢訂單狀態、結單

LINE 通知  Sprint 4
  商家一鍵發 LINE 通知給特定顧客
  使用 LINE Messaging API
```

### 3.2 技術棧

```
前端框架    Next.js 15 (App Router · Turbopack)
UI 語言     React 19 · TypeScript
樣式        Tailwind CSS · design-tokens.css（芮選 Design System）
資料庫      Supabase（PostgreSQL + RLS）
檔案儲存    Supabase Storage
身份驗證    LINE LIFF + LINE Login
AI 文案     Claude API（claude-sonnet 系列）
匯率        ExchangeRate-API（免費方案，每日快取）
部署        Vercel
通知        LINE Messaging API（Sprint 4）
```

## 五、完整 User Flow

### Flow 1：商家建立賣場

```
LINE 登入商家後台
  → 填寫賣場名稱 / 介紹 / 上傳頭像
  → 新增供應商資訊
  → 生成邀請連結
  → 複製連結分享給顧客
```

### Flow 2：商家建立商品

```
從廠商 LINE 群組複製商品原文、下載圖片、確認批發價
  → 進入後台「新增商品」
  → 貼上原始商品文
  → 選擇是否 AI 優化文案
      → AI 分析原文、確保資訊可信度、優化為吸引人的代購文
      → 商家預覽、可手動修改
  → 系統自動偵測規格關鍵字（顏色 / 尺寸 / 材質等），建立多維度規格
  → 確認批發價（選幣別 → 系統換算台幣成本）
  → 填入售價
  → 下拉選擇廠商
  → 上傳商品圖片
  → 儲存 → 商品上架
  → 將商品連結貼回 LINE 群組記事本
```

### Flow 3：顧客註冊流程

```
點擊商家分享的邀請連結
  → 進入顧客前台登入頁（/store/{slug}/login）
  → LINE 快速登入
  → 填寫姓名 / 手機 / LINE ID
  → 送出申請
  → 顯示「已送出申請，待商家核准」
  → 商家在後台顧客管理審核通過
  → 顧客獲得賣場瀏覽權限
```

### Flow 4：顧客下單流程

```
路徑 A（商品連結直接進入）：
  商品連結 → 商品詳細頁 → 選規格 / 數量 → 確認下單彈窗
    → 確認（無購物車，下單即購買）→ 訂單建立 → 查看訂單（狀態：待採買）

路徑 B（賣場首頁瀏覽）：
  賣場首頁 → 商品列表（依類型分類）→ 關鍵字搜尋
    → 商品詳細頁 → 同路徑 A
```

### Flow 5：顧客結單流程

```
登入顧客前台 → 訂單頁面
  → 查看所有訂單 → 篩選「已到貨」商品
  → 勾選要結單的已到貨商品 → 點擊結單
  → 填寫收貨資訊：
      選擇物流方式：
        自取       → 確認取貨時間
        超商店到店 → 填姓名 / 手機 / 超商名稱
        賣貨便     → 填姓名 / 手機 / 超商名稱（現金貨到付款）
        宅配       → 填姓名 / 手機 / 地址（運費預設 NT$210）
      選擇付款方式：
        現金自取 / 匯款（店到店 / 宅配）/ 賣貨便貨到付款
  → 確認送出 → 訂單狀態更新為「已結單」
```

### Flow 6：商家配貨更新流程

```
收到新訂單通知
  → 確認商品供貨商
  → 向廠商下單（填寫下單數量）→ 訂單狀態：已訂購
  → 商品到貨 → 更新到貨數量
  → 選擇配單方式：
      自動配單（按下單時間先後）
      手動配單（部分到貨情況）：
        → 查看該商品的所有訂購顧客
        → 點擊顧客名稱快速查看其所有訂單狀態
        → 手動指定配貨給特定顧客
  → 部分到貨情況：
      若剩餘商品預計 3 週以上才到
        → 系統提示「可通知顧客先出貨」
        → 商家一鍵發 LINE 通知（Sprint 4）或手動 LINE 私訊
        → 顧客確認先出貨 → 該已到商品進入結單流程
  → 配貨完成 → 訂單狀態：已配單
  → 顧客結單 → 訂單狀態：已結單
  → 商家建立出貨單（賣貨便 / 超商 / 宅配）→ 填入物流單號
  → 訂單狀態：已出貨 → 完成
```

## 六、訂單狀態機

```
待採買
  ↓ 商家向廠商下單
已訂購
  ↓ 商品到貨，完成配單
已配單
  ↓ 顧客勾選結單
已結單
  ↓ 商家建立出貨單，填入單號
已出貨
  ↓ 顧客確認收到
已完成
```

**特殊狀態：**
- 部分到貨：同一顧客有多筆訂單，部分已到貨（已配單）、部分尚未到貨（已訂購）
- 取消：顧客取消或商家取消，需記錄原因

## 八、AI 文案優化規格

### 功能描述
商家將廠商提供的原始商品文貼入系統，Claude API 進行優化，產出更吸引買家的代購文案。

### 核心原則（不可違反）
- ❌ 不得添加原文中沒有的功能或特性（如：原文無「不掉色」不能加上去）
- ❌ 不得使用單一來源或可信度不確定的資訊
- ❌ 不得誇大或虛假宣傳
- ✅ 可以修飾語氣、讓文案更流暢吸引人
- ✅ 可以重新組織段落結構
- ✅ 可以補充網路上多來源確認的產品公開資訊

### 優化流程
```
商家貼入原始商品文
  → Claude API 分析原文
  → 產出優化版本
  → 商家預覽（對比原文 vs 優化後）
  → 商家可直接使用 / 手動修改
  → 儲存最終版本
```

### 規格自動偵測
優化完成後，系統自動掃描文案中的規格關鍵字：
- 顏色（色、color、顏色）
- 尺寸（size、尺寸、S/M/L、cm）
- 材質（材質、素材、material）
- 其他維度（口味、容量等）

偵測後自動建立多維度規格選項，商家確認後儲存。

## 九、匯率換算規格

### 支援幣別（MVP）
- 日幣（JPY）
- 英鎊（GBP）
- 美金（USD）
- 港幣（HKD）

### 快取機制
```
每日第一次查詢
  → 呼叫 ExchangeRate-API
  → 存入 exchange_rates table（幣別 + 匯率 + fetched_at）
  → 返回結果給前端

當日後續查詢
  → 查 exchange_rates table
  → fetched_at = 今天 → 直接用快取
  → fetched_at 不是今天 → 重新打 API 更新
```

### 使用情境
商品上架時，批發價欄位旁有幣別選擇器：
```
批發價：¥ 3,800  [幣別：JPY ▼]
              ↓ 今日匯率 0.217
台幣成本：約 NT$ 825
```
商家參考台幣成本後自行填入售價。

## 十、資料追蹤設計（為數據分析預留）

以下欄位在 Sprint 1–4 建立資料模型時就要加入，確保 Sprint 5 有足夠的數據可分析：

```
orders
  ordered_at        timestamptz   下單時間（分析下單時段）

order_items
  product_id        uuid          關聯商品
  supplier_id       uuid          關聯廠商（分析廠商表現）
  quantity          integer       數量
  unit_price        numeric       售價
  unit_cost         numeric       成本

products
  category          text          商品類別（顧客前台分類依據）
  view_count        integer       瀏覽次數
```

## 十二、非功能需求

| 項目 | 要求 |
|------|------|
| RWD | Mobile 375px 優先，支援 Desktop 1280px |
| 載入速度 | 商品列表頁首次載入 < 2 秒 |
| 安全性 | Supabase RLS，每個 table 明確設定存取政策 |
